## SDK and NuGet reference robustness

Compilation currently discovers reference assemblies from the NuGet cache and the installed .NET SDK,
which couples builds to the host machine layout. Evaluate a more explicit model: vendor or embed the
required .NET 10 assemblies, resolve them from a pinned source, or compile the needed SDK pieces
in-repo.

## User generators and analyzers under AOT

The AOT compiler cannot currently load user-space source generators and analyzers. Candidate designs:

- register native generators at AOT-compile time;
- run generators/analyzers through a Roslyn transformation and register the emitted `.g.cs` sources.

The isolation and discovery story for user analyzers remains open.

## Compiler bootstrap chain

- Microsoft compiler -> AOT sharp compiler (works).
- AOT sharp compiler -> JIT sharp compiler (works; not a single executable).
- AOT sharp compiler -> AOT sharp compiler (not implemented). Requires a way to execute user
  generators/analyzers, either as native libraries or through an interpreter.

## Embedded SDK payload

Keep the payload out of a giant C# string literal and out of the project file. Two options:

- **Base64 `u8` literal in a generated file**: emit a `.designer.cs`/`.g.cs` file with
  `<auto-generated />`, warning pragmas, and `.editorconfig` `generated_code = true`. The `u8` span
  avoids the UTF-16 string heap and `Base64.DecodeFromUtf8` is SIMD-accelerated. Cost: about 33% size
  growth, git history bloat, and editor lag; suitable only for rarely changed payloads.
- **Source generator resource embedding**: embed the binary as a manifest resource and generate a
  small accessor, so no text inflation and no `.csproj` edits. Open questions: where the payload is
  discovered (solution folder, environment variable, project root) and how a missing payload is
  reported at compile time.
